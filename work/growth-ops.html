Case study · Internal tool

Growth ops agent

A small agent system that runs the daily work of paid growth: reviewing ad performance, writing creative briefs, planning tests and rolling up the week. It recommends. A person decides.

Role
Designed and built solo
Stack
Python (standard library), Claude, Codex, OpenRouter
Size
About 400 lines, plus skills written as plain files
The problem

Growth work is a loop.

Most of a growth marketer's week repeats: read the numbers, decide what to scale and what to cut, brief new creative, plan the next test, and report. Each step is structured enough to hand to a model. None of them should touch an ad account on their own.

I wanted the loop to run on a schedule, leave a written trail I could check, and stop short of anything that sends, spends or publishes.

The loop

What runs, and when.

Scheduled skills run on their own. The rest run when I ask. Every output is a markdown file, so it can be read, compared and edited like any other document.

  1. Plan todayWeekdays 8:00. Top three priorities, and which ad tests are due to read out.
  2. Ad performance reviewWeekdays 9:00. Every ad set labelled Scale, Hold, Fix or Kill.
  3. Creative briefOn request. Ten new concepts plus iterations of the current winner.
  4. A/B test planOn request. Hypothesis, metrics, sample size and the decision rule.
  5. Weekly growth reviewMondays 10:00. Spend against target, learnings, next week's tests.

↺ Concluded tests are written back into each product's notes, so next week's briefs start from what was learned.

Skills

Each skill is a written procedure.

A skill is a short plain-text file: when it runs, what it reads, what it must produce and what it must never do. Adding a new one means writing a new file. No code changes.

weekdays 9:00Ad performance review

Compares campaigns, ad sets and ads on spend, CPA, ROAS, CTR, hook rate and frequency over 1, 3 and 7 days. Shows the number behind every Scale / Hold / Fix / Kill call, and flags anything under about 50 conversions as low confidence.

→ reports/ad-review-<product>-<date>.md
on requestCreative brief

Ten concepts, each with an angle, a three-second hook, a format, the audience pain it hits and what it tests. Starts from the latest performance review.

→ reports/creative-brief-<product>-<date>.md
on requestA/B test plan

Hypothesis, variants, primary and guardrail metrics, sample size and run time with the assumptions stated, stop rules and the decision rule.

→ research/test-<product>-<slug>.md
on requestFunnel audit

Maps ad → landing page → checkout → activation, finds the biggest drop-off at each step and ranks a test backlog by impact, confidence and ease.

→ reports/funnel-audit-<product>-<date>.md
on requestCompetitor ad research

Finds competitors' long-running ads, which signal that they work, and notes angle, hook, offer and format. Ends with what to steal, what to avoid and how to stand apart.

→ research/competitors-<product>-<date>.md
mondays 10:00Weekly growth review

Rolls up the week's reviews and tests: spend, CPA and ROAS against target, what was learned and next week's test queue. Proposes priorities but doesn't add them.

→ reports/weekly-growth-<date>.md
Routing

The cheapest tier that can do the job.

Every request is sorted before any model is called. Most status questions never reach a model.

tier 1Rules

Status, priorities and the skills list are answered from files. No model call.

tier 2Fast model

Short questions get a quick answer from a small model.

tier 3Skill + strong model

Anything matching a skill, or real work, runs with that skill's procedure and access to the notes.

Models sit behind a fallback chain. If one is capped, out of credit or fails, the next one takes the request, and the reason is shown.

OpenRouter→Codex→Hermes→Claude Code→Claude API
Guardrails

Recommend only.

  • Never send, spend or publish. Every model call carries this rule. Work is drafted and stops for approval.
  • No changes to the ad account. The performance review can't change budgets, pause ads or edit campaigns. It only recommends.
  • Updates to people need sign-off. Stakeholder updates are drafted, then wait for approval before going anywhere.
  • Every request leaves a receipt. Time, tier, model and output are logged, so any answer can be traced.
  • Secrets stay where they are. API keys are read in place when needed and never copied, cached or logged. The dashboard only shows which keys exist.
  • It can watch, not act. It reports the status and recent errors of the other systems I run. For the trading bot it is explicitly barred from placing, cancelling or changing orders.
Why it's built this way

Plain files, small code.

Markdown as memory. Priorities, product notes, reports and receipts are all plain files. I can read them, any agent can work in them, and nothing is locked in a database.

Procedures as files. Writing a skill is closer to writing a good brief than writing code, and anyone who knows the work can review it.

No dependencies. The router and dashboard are about 400 lines of standard-library Python, so there's very little that can break.
